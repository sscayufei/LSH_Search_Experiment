## 实验控制与正确性

固定 tau=0.75、k=12、L=32、seed=42，使用 Phase 5 相同的全部 100 条语义测试查询与向量。
查询文本没有进入任一新增库，所有查询始终走语义路径，不混入 Exact 提前返回的成本优势。
各规模先对该全库重算 Ground Truth，不能沿用 10k 的相关集合；随后释放暴力工作矩阵再构建混合索引。
三个规模各用独立进程，避免索引和对象遍历产生的累计内存滞留；未并行启动多个大规模索引。

各规模生成的超平面字节 SHA-256 完全相同，保证哈希函数不随 N 改变。
每张表每个历史 ID 恰好出现一次；旧候选集合与旧 Ground Truth 均为扩展后集合的子集。
精筛仍只计算去重候选，逐查询核验结果为 C∩G，比较次数恰为 |C|。
N=10k 的候选和返回 ID 与 Phase 5 一致，确认保留同一算法基线。

每规模热身 2 轮、测量 5 轮、单线程；每轮固定种子打乱查询顺序。
计时为预编码查询的完整混合 API，数据加载/编码、全库核验、索引构建、内存遍历和绘图不计入。
内存口径与 Phase 5 相同：估算额外 Exact+LSH 唯一对象，排除共享原文对象和归一化历史工作矩阵；不是 RSS 或峰值。
工作矩阵在每个规模单列。Phase 6 时延属于新一次单方法规模实验，没有覆盖或替代 Phase 5 的三方法计时。

## 为什么固定 k/L 时无关候选可能近似线性增长

对某查询，令 I_i 表示某条低于阈值的历史向量是否进入候选，F=sum I_i。
随机超平面模型下，其期望为：

```text
p(s) = 1 - acos(s)/pi
P(s;k,L) = 1 - (1-p(s)^k)^L
E[F(q)] = sum_{i not in G(q)} P(sim(q,x_i);k,L)
```

期望的可加性不要求不同历史向量的碰撞相互独立；相关性仍会影响方差、拥挤桶和长尾。
若扩容后背景相似度分布近似稳定、相关项占比较小，平均每项误候选概率可近似保持常数 P_false，
于是 E[F]≈N·P_false。固定 k/L 不会仅因库变大自动降低一条背景向量的碰撞概率。
因此数量可能线性增加，而候选比例可能近似不变；背景密度或分布改变时，此近似可能失效。

## 可讨论的改进及风险（均未实现）

- 随 N 增大适当增加 k：减少背景碰撞，但也降低阈值附近相关项的候选召回。
  小概率近似下 E[F]≈NL·p0^k，若 N 增 g 倍、L 不变，维持预算需增加约 log(g)/(-log p0) 个 bit。
  例如 p0=0.5、g=10 时约需 3.322 bit，整数约取 4；这是理论推导，不是本轮调参。
  增加 L 补偿召回又会增加内存、查表和候选，需要重新做验证集取舍。
- 对拥挤桶做二级散列/分裂：可能减少候选和长尾耗时，但路由需一致，硬截断会损失 Recall，二级元数据也占空间。
- 较少表配合 multi-probe：可能降低表内存并弥补召回，但多探测会增加查询访问和候选，不保证候选增长消失。

这些只是作用与风险说明，未编写改进实现或宣称测得收益；若以后实现，须经人工选择并在同一查询/基线上比较四项指标。

## 数据结构、复杂度与产物

文本列表保持原 ID，set 去重/排除查询，固定随机排列控制扩展顺序，新增来源以数据行/列定位。
总输入字符长度 T、唯一扩展数 U 时，去重平均 O(T)、打乱 O(U)，文本记录内存 O(U) 加实际字符存储。
Embedding 按真实 token/模型成本计算，以分块控制临时张量；最终向量磁盘空间 O(Nd)，memmap 避免同时持有两份输出。
每规模 Ground Truth O(QNd) 时间，只保留相关 ID，不持有完整 Q×N 得分矩阵。
基线索引仍为 O(NLkd) 建表、O(Lkd+NL) 额外索引空间；查询 O(Lkd+B+c log c+cd)。
独立进程只控制测量资源，不是检索算法改进。

保存 data/scale/corpus.jsonl、corpus_embeddings.npy、encoding_chunks.json 和 manifest.json，包含编码耗时、版本、来源和 SHA-256。
results/raw/scale_summary.csv 保存三组实测，scale_predictions.csv 只保存分类预测；
各 scale_nN/ 保存 100 行指标、500 条原始计时、候选/返回/Ground Truth ID、32 张表诊断及检查信息。
三组共 300 行查询指标和 1,500 条真实计时。
scale_manifest.json、scale_plan.json、scale_resource_preflight.json 和 scale_analysis.log 保留计划、资源、过程及输入/输出/代码追溯。

scale_analysis.png 用实线/点表示实测、虚线/点线表示外推或理论，时间与索引空间面板只画实测规模。
scale_diagnostics.png 展示候选比例、拥挤桶和条件 Recall，均已视觉检查。
诊断图端点标签曾偏挤，使用 render_scale 只重绘标签位置；所有数值产物哈希前后完全一致，
原绘图代码/图像哈希及新绘图代码追溯记录在 scale_manifest.json 的 render_only_update 中。
